# Архитектура веб-сервиса

## Структура сервиса

Два раздела в верхнем меню.

### Раздел 1. «Проекты» (главный экран)

- Список ЖК (финансовых моделей): поиск, фильтры, сортировка, сравнение 2–3 проектов, создание, копирование, архивация (см. «Операции с проектом»).
- Внутри проекта — вкладки: **Исходные данные, ТЭП, Бюджет, План продаж, Эскроу, Финансирование, Налоги, CF, Дашборд, Версии, Выгрузка в Excel**.
- **Проектные источники** хранятся внутри проекта и в общий справочник не попадают: ГПЗУ, ППТ, ТЭП архитектора, договор на участок, term sheet банка, выборка аналогов для этого ЖК, экспертные оценки. У каждого — вложение (Vercel Blob), автор, дата (docs/00, раздел 6).
- **Паспорт показателя** открывается по клику на любое число внутри проекта. Из паспорта — ссылки на формулу и общие источники в Справочнике (в той версии справочника, на которой посчитана версия проекта) и на проектные источники.

### Раздел 2. «Справочник» (общий для всех проектов, с версиями)

| Подраздел | Что показывает | Откуда |
|---|---|---|
| Методика | Все формулы: выражение, «почему так», отклонённые варианты, источники, контрольный пример, значение за прошлый месяц | `formulas.yaml` |
| Нормативы и ставки | Общие параметры (`scope: template`) и региональные (`scope: region`): налоги, ключевая ставка, индексы, НЦС, нормативы парковок, ставки земельного налога | `parameters.yaml`, `capex_items.yaml`, `regions.yaml` |
| Источники | Реестр общих источников (законы, НПА, статистика, госсервисы) с кликабельными ссылками | `sources.yaml`, `scope: global` |
| Бенчмарки | (а) Расценки компании по завершённым проектам; (б) аналоги рынка | БД: `company_benchmarks`, `market_comps` |
| Журнал изменений | Кто, что, когда поменял, с обоснованием, и какие проекты это затрагивает | БД: `reference_versions`, `audit_log` |

У каждого подраздела есть переключатель версии справочника: по умолчанию — текущая опубликованная, можно открыть любую прошлую.

| Слой | Выбор | Почему |

| Спецификация | `packages/spec` — YAML из `data/` компилируется в типизированный JSON, схемы `zod` | Код не может сослаться на несуществующий параметр/источник — ошибка сборки |
| БД | Postgres (Neon через Vercel Marketplace) + Drizzle ORM | Проекты, версии расчётов, значения параметров, журнал изменений |

| Экспорт | `exceljs` в `packages/export` | Выгрузка проекта в .xlsx с живыми формулами и листом «Источники» для банка/инвестора |
| Графики | Recharts | Дашборд |
| Тесты | Vitest + Playwright | Юнит-тесты формул, золотые кейсы, e2e |
| CI | GitHub Actions | `validate_spec` → typecheck → tests → Vercel preview |

## Расчётное ядро

- Вход: `ProjectInput` (значения параметров + ссылки на источники для project-параметров) и версия справочника (`spec_version`).
- Каждая формула из `formulas.yaml` — отдельная функция `F_<MODULE>_<NAME>(ctx)`, её ID совпадает с ID в YAML. Тест проверяет, что у каждой формулы в YAML есть реализация и наоборот.
- Порядок вычислений — топологическая сортировка по `depends_on`. Циклы запрещены (ставка ПФ берёт покрытие прошлого месяца).
- Выход: `ResultSet` — значения всех узлов + `trace` (для каждого узла: формула, входы, их значения). Из `trace` строится паспорт показателя.
- Никаких чисел в коде, кроме 0, 1 и математических констант. Линтер-правило + тест на поиск литералов в `packages/engine/src/modules`.

## Данные в БД

Сервис многопроектный: у каждого ЖК своя финансовая модель. Расчёт всегда воспроизводим по неизменяемому снимку (`project_versions`).

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Пользователи | `id`, `name`, `email`, `role` (`admin` — администратор/методолог, `analyst` — аналитик, `viewer` — наблюдатель), `active`, `created_at` |
| `projects` | Карточка проекта (ЖК) | `id` (uuid), `name`, `region_code` (из `data/regions.yaml`), `oktmo`, `cadastral_number`, `housing_class` (enum из `GEN.HOUSING_CLASS`), `stage` (`GEN.PROJECT_STAGE`), `status`, `owner_id` (аналитик — автор), `copied_from_project_id`, `current_version_id`, `created_by`, `created_at`, `updated_by`, `updated_at` |
| `project_versions` | Неизменяемый снимок расчёта | `id`, `project_id`, `number` (1, 2, …), `label`, `scenario`, `reference_version_id` (версия справочника, на которой посчитано), `inputs` (jsonb, снимок `ProjectInput` вместе с проектными источниками и выборками бенчмарков), `result` (jsonb `ResultSet` или ссылка на Blob при большом объёме), `kpi_summary` (jsonb: выручка, NPV, IRR акционера, маржа, пиковый капитал, LLCR, статус F.CHECK.ALL), `checks_passed`, `reason` (`input_change` / `reference_update` / `copy`), `created_by`, `created_at` |
| `parameter_values` | Текущие (рабочие) значения параметров проекта | `project_id`, `param_id` (ID из `parameters.yaml`), `value` (jsonb), `source_id` (общий или проектный источник), `benchmark_query` (jsonb — фильтр выборки бенчмарков, если значение взято из неё), `author`, `rationale`, `min`, `max` (для уровня 5 обязательны `author`, `rationale`, `min`, `max`), `updated_by`, `updated_at` |
| `sources` | Источники: общие и проектные | `id`, `scope` (`global` / `project`), `project_id` (только для `project`), `kind` (для проектных: ГПЗУ, ППТ, ТЭП архитектора, договор на участок, term sheet банка, выборка аналогов, экспертная оценка), `template_source_id` (тип из `sources.yaml`: `S_PROJECT_DOCS`, `S_BANK_TERMSHEET`, `S_EXPERT`), `level`, `title`, `issuer`, `url`, `attachment_id`, `used_for`, `accessed`, `verified`, `note`, `author`, `created_at`; для общих — `reference_version_from`, `reference_version_to` |
| `attachments` | Вложения (Vercel Blob) | `id`, `project_id` (null — вложение справочника, например документ бенчмарка), `blob_url`, `file_name`, `uploaded_by`, `uploaded_at` |
| `reference_versions` | Версии справочника | `id`, `spec_version` (номер/хеш), `status` (`draft` / `published`), `base_version_id`, `published_at`, `author_id`, `reason` (обоснование), `changes` (jsonb: сущность, ID, поле, было → стало, источник), `content` (jsonb — полный снимок методики, нормативов и общих источников), `affected_projects` (jsonb, вычисляется при публикации) |
| `company_benchmarks` | Расценки компании по завершённым проектам | `id`, `capex_item_id` (статья из `capex_items.yaml`), `project_name`, `housing_class`, `region_code`, `year`, `rate` (руб/ед.), `base` (база статьи), `unit`, `price_date`, `vat_included`, `document_kind` (смета / договор / КС-2), `attachment_id` или `url`, `author`, `reference_version_from`, `reference_version_to` |
| `market_comps` | Аналоги рынка | `id`, `name` (ЖК), `region_code`, `housing_class`, `address`, `price_per_m2` (цена ДДУ, руб/м²), `pace_m2_per_month` (темп продаж), `observed_at` (дата), `source_id` (ЕИСЖС или другой общий источник), `url`, `author`, `reference_version_from`, `reference_version_to` |
| `change_requests` | Заявки аналитиков на изменение Справочника | `id`, `author_id`, `target` (jsonb: сущность, ID, поле), `proposed_value`, `rationale`, `source_url` или `attachment_id`, `status` (`new` / `accepted` / `rejected`), `reviewer_id`, `decision_comment`, `reference_version_id` (в какой версии принято), `created_at`, `decided_at` |
| `audit_log` | Журнал: кто, что, когда | `project_id` (null — действие в Справочнике), `user_id`, `action` (create / rename / copy / status / param_change / source_add / calculate / reference_update / export / reference_edit / reference_publish / change_request), `payload` (jsonb: было → стало, обоснование), `at` |

Регион проекта — это код из `data/regions.yaml`. Региональные параметры при создании проекта подставляются из текущей опубликованной версии справочника; если поле региона `null` (статус `structure_only` / `to_fill`), параметр становится обязательным для ручного ввода с документом (`needs_verification`), см. CLAUDE.md п. 8.

### Статусы проекта

| Статус | Код | Что можно делать |
|---|---|---|
| Черновик | `draft` | Всё: ввод, расчёт, переименование |
| В работе | `in_progress` | Ввод и расчёт |
| Утверждён | `approved` | Только чтение. Утверждается конкретная версия (`current_version_id`); чтобы изменить — вернуть в «В работе» (фиксируется в журнале) или скопировать проект |
| Архив | `archived` | Только чтение, скрыт из списка по умолчанию (фильтр «Архив»); можно открыть, скопировать, выгрузить в Excel и вернуть из архива в статус, который был до архивации |

Переходы: `draft → in_progress → approved`, любой → `archived`, `archived →` статус до архивации, `approved → in_progress`. Каждый переход пишется в `audit_log`. Утверждать и возвращать из «Утверждён» может автор проекта (аналитик) и администратор; наблюдатель — нет (см. «Роли и права»). До этапа «Роли, права, журнал изменений» — любой вошедший пользователь.

### Операции с проектом

- **Создать** — мастер, шаг 1: название, регион (`GEN.REGION_CODE`), кадастровый номер (`GEN.CADASTRAL_NUMBER`), класс (`GEN.HOUSING_CLASS`). Создаётся `projects` в статусе `draft` и `parameter_values` с региональными значениями из `regions.yaml` (с их `source_ids`).
- **Переименовать** — меняет `projects.name` (= `GEN.PROJECT_NAME`), запись в журнал.
- **Скопировать** — новый проект (`draft`, `copied_from_project_id` = исходный, имя «<имя> (копия)»): копируются все `parameter_values` и проектные источники (`sources.scope = project`) со ссылками на те же вложения; версии и журнал не копируются. Копия считается на текущей опубликованной версии справочника. Используется для вариантов концепции.
- **Архивировать / вернуть из архива** — смена статуса.
- **Удалить** — с подтверждением (решение владельца продукта пересмотрено 25.09.2026; до пересмотра — «только архив»). Для сохранения доступа к проекту используйте «Архивировать».
- **Сравнить** — 2–3 проекта: `kpi_summary` их текущих версий на одном экране + ключевые входы (регион, класс, площадь участка, продаваемая площадь).

### Список проектов

Главная страница `/` — таблица/карточки: название, регион, класс, площадь участка (`LAND.AREA`), выручка (`F.SALES.REVENUE_TOTAL`), NPV (`F.KPI.NPV`), IRR акционера (`F.KPI.IRR`), маржа (`F.KPI.MARGIN`), статус, дата изменения, автор. Показатели берутся **только** из `project_versions.kpi_summary` текущей версии — того же `ResultSet`, что и дашборд проекта, поэтому числа совпадают. Если входы изменены после последнего расчёта, в строке показывается «пересчитать». Поиск по названию/кадастровому номеру, фильтры (регион, статус, класс), сортировка по любому столбцу (на сервере, SQL).

Демо-проект: `tests/cases/derbenevskaya_legacy.yaml` загружается сид-скриптом как проект «Дербеневская (демо)» в расчёте «как в исходном Excel».

## Экспорт в Excel

Модуль `packages/export` — чистый TypeScript на `exceljs`, на входе `ProjectInput` + `ResultSet` + реестры `packages/spec`, на выходе буфер .xlsx. Вызывается из API-маршрута `apps/web` (`GET /api/projects/:id/export?version=`), кнопка «Скачать в Excel» — на странице проекта и в строке списка.

Имя файла: `<Название ЖК>_финмодель_<ГГГГ-ММ-ДД>.xlsx` (символы, недопустимые в именах файлов, заменяются на `_`).

| # | Лист | Содержание |
|---|---|---|
| 1 | Обложка | Проект, дата расчёта, номер версии проекта, версия справочника (`spec_version`), сценарий, автор, статус F.CHECK.ALL |
| 2 | Исходные данные | Каждый параметр: ID, название, значение, единица, источник, уровень, ссылка (гиперссылка), дата проверки, обоснование; для уровня 5 — автор и диапазон |
| 3 | Источники | Два блока: общие источники, использованные в проекте (с версией справочника), и проектные источники (тип, автор, дата, ссылка на вложение); гиперссылки кликабельны |
| 4 | ТЭП | F.TEP.* |
| 5 | Бюджет | Статьи: ставка × база × индекс = сумма (живая формула) |
| 6 | План продаж | По продуктам и очередям |
| 7 | Эскроу | По очередям |
| 8 | Финансирование | Выборка, ставка, проценты, погашение, остаток долга |
| 9 | Налоги | НДС, налог на прибыль, земельный налог |
| 10 | CF (мес) | Помесячно |
| 11 | CF (кв) | Агрегат по кварталам: `SUMIFS` по листу «CF (мес)» |
| 12 | CF (год) | Агрегат по годам: `SUMIFS` по листу «CF (мес)» |
| 13 | Дашборд | Ключевые показатели + графики |
| 14 | Проверки | Результат F.CHECK.ALL: проверка, результат, значение, допуск |

Правила листов:

- **Живые формулы** там, где Excel может воспроизвести расчёт: итоги и суммы (`SUM`), ставка × база × индекс, остатки (`остаток на начало + приход − расход`), агрегаты CF по кварталам и годам, ссылки между листами. Показатели, требующие итераций или функций, которых нет в Excel в той же постановке (ставка ПФ с К1/К2, XIRR по месяцам), пишутся значением, рядом — ID формулы и пометка «значение из сервиса». Каждая ячейка с формулой содержит и кэшированный результат из `ResultSet`, чтобы файл сразу открывался с числами.
- **Рядом с каждой строкой** — столбцы «ID формулы» и «Описание» (`name` и `expr` из `formulas.yaml`).
- **Оформление**: ввод — синий шрифт, формулы — чёрный, ссылки на другие листы — зелёный; закреплённые шапки; формат `# ##0 ₽` для рублей, `0,00%` для долей, `ДД.ММ.ГГГГ` для дат; даты — настоящие даты Excel; форматирование только в используемом диапазоне (никаких столбцов до XFD).
- **Графики** на листе «Дашборд»: `exceljs` не создаёт диаграммы, поэтому данные графиков лежат таблицами на листе, а сами диаграммы добавляются в файл постобработкой (DrawingML-диаграммы Excel, связанные с этими таблицами), чтобы они оставались «живыми».

Проверка совпадения (тест `packages/export`): для демо-проекта и синтетического кейса (1) каждая ячейка-итог содержит кэш, равный `ResultSet` до 1 руб.; (2) файл пересчитывается LibreOffice в headless-режиме (в CI), и пересчитанные итоги (выручка, бюджет, CF, долг на конец) совпадают с сервисом до 1 руб.; (3) все гиперссылки листа «Источники» — `http(s)://`; (4) ни на одном листе нет ошибок `#REF!`, `#VALUE!`, `#DIV/0!`, `#NAME?`.

Импорт «Загрузить из Excel» — отдельный этап, только по запросу владельца продукта.

## Справочник и его версии

### Где хранится справочник

Предлагаемое решение (требует подтверждения владельца продукта, см. «Открытые вопросы»):

- `data/*.yaml` в git — исходное наполнение справочника (версия 1) и структура: какие параметры и формулы существуют.
- Значения нормативов и ставок, тексты методики (`rationale`, `rejected`), общие источники и бенчмарки методолог правит в интерфейсе.
- **Логика формул** (решение владельца продукта 25.09.2026, вариант «б»): в интерфейсе методолог меняет все числа, пороги и выбор между заранее заложенными в коде вариантами расчёта (например, «медиана / средневзвешенная»). Новая логика формулы — через разработку: сначала `formulas.yaml` (с `rationale` и `rejected`), затем код; публикуется новой версией справочника вместе с релизом. Каждая формула остаётся функцией в коде, проверенной тестами (CLAUDE.md, правило 2). Правки копятся в черновике версии (`reference_versions.status = draft`) и публикуются одной кнопкой с обоснованием.
- Опубликованная версия неизменяема и хранит полный снимок (`content`). Каждая опубликованная версия выгружается в `data/*.yaml` автоматическим PR, чтобы git, `validate_spec.py` и `docs/03–05` оставались актуальными.
- Перед публикацией выполняются те же проверки, что в `validate_spec.py` (`packages/spec/src/checks.ts`): источники существуют, у уровней 1–3 есть URL, граф формул без циклов. Версию с ошибками опубликовать нельзя.

### Актуализация справочника

Ежеквартально или по событию (решение ЦБ по ключевой ставке, новый прогноз МЭР, новые НЦС, изменение закона): методолог обновляет значения и дату проверки источников (`accessed`), проверки проходят без ошибок, версия публикуется. Старые версии проектов продолжают ссылаться на свою версию справочника.

**Источники, требующие перепроверки (решение владельца продукта 27.09.2026).** В разделе «Источники» общий источник отмечается красным, если: (а) `verified: false` — значение и ссылка ещё не сверены с текстом документа («не сверен»); или (б) с даты проверки `accessed` прошло больше 3 месяцев — одного цикла актуализации («устарел»). Счётчик таких источников показывается у каждого подраздела; есть фильтр «только требующие перепроверки». Источники без даты проверки (типы проектных документов, данные компании) не отмечаются.

**Статус сверки в интерфейсе (решение владельца продукта 27.09.2026).** У каждого общего источника — выпадающий список «Не сверен / Сверен». «Сверен» делает источник сверенным (`verified: true`) и ставит дату проверки `accessed` = сегодня (повторный выбор снимает отметку «устарел»); «Не сверен» — источник требует сверки. До этапа 12 (роли) статус может менять любой вошедший пользователь. В демо-режиме выбор хранится до перезагрузки страницы; с этапа 7 — в базе, как изменение справочника с автором и датой (попадает в журнал изменений справочника).

### Публикация новой версии

1. Методолог вносит изменения: у каждого — обоснование и источник.
2. При публикации сервис определяет затронутые проекты: у текущей версии проекта в `trace` есть изменённый параметр, формула, источник или выборка бенчмарков.
3. Для каждого затронутого проекта выполняется пробный пересчёт текущих входов на новой версии (без сохранения). Разница NPV, IRR акционера и маржи сохраняется в `reference_versions.affected_projects`.
4. Запись попадает в журнал изменений справочника.

### Поведение проекта при обновлении справочника

- Проект **не пересчитывается автоматически**. Все его версии остаются посчитанными на своей версии справочника и воспроизводятся с тем же результатом.
- На карточке проекта и в строке списка — уведомление «Доступна новая версия справочника»: номер версии, список изменений, которые затрагивают проект, и влияние на NPV / IRR / маржу из пробного пересчёта.
- Кнопка «Пересчитать» создаёт новую версию проекта (`reason = reference_update`) на новой версии справочника. Старая версия сохраняется и доступна во вкладке «Версии».
- **Утверждённый проект** пересчитывается только после отдельного подтверждения («Проект утверждён. Пересчитать на новой версии справочника?»). После пересчёта проект переходит в статус «В работе», утверждённая версия остаётся в истории; новую версию нужно утвердить заново (решение владельца продукта 25.09.2026).
- Проекты в архиве уведомление не показывают; при возврате из архива оно появляется.
- Если новая версия не затрагивает проект, уведомления нет, проект продолжает ссылаться на свою версию.

### Бенчмарки

Правила статистики — формулы `F.BENCH.*` и параметры `BENCH.*` (docs/00, раздел 9; docs/03 — модуль BENCH). Значения параметров меняет только методолог.

**Аналоги рынка** (`market_comps`) — ЖК-аналоги: название, регион, класс, адрес, цена ДДУ руб/м², темп продаж, дата, источник (ЕИСЖС или другой общий источник), ссылка.

- В проекте аналитик собирает выборку (`BENCH.MARKET_SAMPLE`, проектный источник «выборка аналогов») и корректировки (`BENCH.PRICE_ADJUSTMENTS`). Результат — стартовая цена (`F.BENCH.MARKET_PRICE` → `SALES.PRODUCTS.start_price`) и темп (`F.BENCH.MARKET_PACE` → `SALES.PACE`), уровень 3.

**Расценки компании** (`company_benchmarks`) — факт по завершённым проектам: статья бюджета, проект, класс, регион, год, сумма и база, ссылка на документ (смета, договор, КС-2).

- В проекте — выборка по статье (`BENCH.COST_SAMPLE`); результат — ставка статьи (`F.BENCH.COST_BENCH`), уровень 4. Если сопоставимых проектов меньше `BENCH.COST_MIN_PROJECTS` — предлагается значение по НЦС с пометкой «экспертное».

**Общее:** статистика выборки и предупреждения — `F.BENCH.STATS`; выбросы подсвечиваются и исключаются только вручную с причиной (в журнал); выборка замораживается в версии проекта; в паспорте показателя видны аналоги, веса и корректировки.

### Доступ к сервису

**Этапы 7–11:** вход по ссылке и общему паролю команды (переменная Vercel `APP_PASSWORD`, секрет cookie — `APP_SESSION_SECRET`), затем пользователь один раз вводит имя. Имя записывается автором изменений. Сессия — 30 дней, после неверного пароля — задержка перед повторной попыткой. Все вошедшие имеют права аналитика на все проекты.

**С этапа 12 — личный пароль без логина** (решение владельца продукта 25.09.2026):

- Администратор создаёт пользователя (имя, роль). Сервис сам генерирует длинный случайный пароль (не менее 20 символов) и показывает его один раз; администратор передаёт его пользователю. Придумывать пароль самому нельзя — иначе пароли становятся угадываемыми и могут совпасть.
- Вход — одно поле «Пароль»: по паролю сервис определяет, кто вошёл и с какой ролью.
- В базе хранится не пароль, а его отпечаток HMAC-SHA256 с секретом сервера (переменная Vercel `APP_PASSWORD_PEPPER`); отпечатки уникальны.
- Защита от подбора: задержка и временная блокировка после серии неверных попыток с одного адреса.
- Администратор может перевыпустить пароль (старый перестаёт работать) и отключить пользователя.
- Общий пароль отменяется.
