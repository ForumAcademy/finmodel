# CLAUDE.md — правила работы в репозитории сервиса оценки участка

Проект: веб-сервис оценки потенциала земельного участка под жилую застройку. Регионы первой очереди — Москва и Московская область (два отдельных региона). Next.js + TypeScript, отдельный проект на Vercel, код на GitHub. Полное задание — `docs/06_zadanie.md`.

Пользователь сервиса — финансист девелопера и руководитель проекта, не разработчик. Репозиторий, PR, деплой и проверки ведёт Claude.

Старый репозиторий `ForumAcademy/financialmodelstroyka` — только источник. **В нём ничего не менять.**

## Главный принцип

**Каждое число в расчёте объяснимо и имеет источник со ссылкой.** Если значение нельзя связать с параметром из `data/parameters.yaml` (у которого есть `source_ids`) или с формулой из `data/formulas.yaml`, его нельзя добавлять в код.

## Источник правды

- `data/sources.yaml` — источники (уровень 1–5, URL, дата проверки).
- `data/parameters.yaml`, `data/capex_items.yaml`, `data/regions.yaml`, `data/company_assumptions.yaml` — исходные параметры.
- `data/formulas.yaml` — формулы: `expr`, `depends_on`, `rationale`, `rejected`, `source_ids`, `example`.
- `docs/03–05` генерируются командой `python scripts/render_docs.py` и в git не хранятся (`.gitignore`). CI собирает их на каждом прогоне и выкладывает артефактом `docs-03-05`. **Не редактируй и не коммить их.**
- `docs/00_principles.md`, `01_architecture.md`, `02_legacy_audit.md` — пишутся руками.
- `legacy/` — исходный Excel и полная карта его ячеек. Ни одно значение не удалять.

## Устройство репозитория

- `packages/spec` — справочник из `data/*.yaml` со схемами и типами ID.
- `packages/engine` — расчётное ядро: `src/modules` — формулы (одна формула = одна функция), `src/project.ts` — расчёт проекта целиком (вводные, стандарт компании, горизонт, режимы), `src/explain` — пояснения «Как посчитано», сводка продаж, периоды отчётов.
- `packages/excel-import` — загрузка готовой финмодели из Excel по карте `legacy/legacy_values_map.csv`.
- `packages/egrn-import` — распознавание выписки ЕГРН (XML, ZIP Росреестра, текст PDF) в поля участка.
- `packages/engine/src/plot.ts` — участок проекта: поля, метки происхождения, новый проект (с кадастровым номером и без), «было → стало», история; `src/reference.ts` — строки экрана «Справочник».
- `packages/engine/src/book.ts` — справочник в браузере: правка стандартных значений новой версией, файл справочника, версия справочника у проекта и «Обновить»; `src/projectfile.ts` — файл проекта (формат — docs/01, «Хранение сейчас»).
- `apps/web` — интерфейс. Проекты, документы и справочник хранятся в браузере (`apps/web/lib/store.ts`, IndexedDB) и передаются коллегам файлами (`apps/web/lib/files.ts`); отдельной базы нет (решение пользователя 29.09.2026). **В интерфейсе нет расчётов**: экраны только вызывают ядро и показывают результат. Любая арифметика над результатами (итоги, доли, пересчёт по периодам, примеры в пояснениях) — в ядре, с тестом.

## Обязательные правила

1. **Нет магических чисел.** В `packages/engine/src/modules/**` запрещены числовые литералы, кроме `0`, `1`, `12`, `365` и индексов. Ставки, коэффициенты, пороги берутся только из параметров по ID.
2. **Одна формула = одна функция.** ID функции совпадает с ID формулы (`F.FIN.RATE` → `F_FIN_RATE`). Реализация повторяет `expr` из YAML. Если нужно изменить логику — сначала изменение в `data/formulas.yaml` (с `rationale` и `rejected`), затем код.
3. **Новый параметр** добавляется в `parameters.yaml` со всеми полями: `unit`, `kind`, `scope`, `source_ids` (≥1, существующие), `basis`, `status`, `legacy` (ячейка исходника или `new`).
4. **Источники делятся на общие и проектные** (`scope: global | project`, docs/00 раздел 6). Конкретные документы проекта (выписка ЕГРН, ГПЗУ, ППТ, ТЭП, договор, условия банка, экспертная оценка) хранятся в проекте, в `data/sources.yaml` — только их типы. **Новый общий источник** уровня 1–3 — только с URL на первичный документ (КонсультантПлюс, Гарант, pravo.gov.ru, сайты ЦБ, Минстроя, МЭР, ФНС, ЕИСЖС). Новости и обзоры допустимы временно, с `verified: false` и `note`.
5. **Нельзя удалять значения исходного Excel молча.** Карта `legacy/legacy_values_map.csv` и `legacy_formulas_map.csv` должна оставаться полной (`scripts/build_legacy_map.py` завершается с кодом 0).
6. **Даты — только даты.** Деньги — рубли (`decimal.js`), доли — доли.
7. **Не выдумывай нормативы, ставки и источники.** Если ставка или норматив региона неизвестны — оставь `null`, статус `needs_verification`, в интерфейсе — обязательный ручной ввод с документом. Нет источника — вопрос пользователю.
8. **Регион добавляется данными, а не кодом** (`data/regions.yaml`).
9. **Один этап — одна ветка и один PR.** Не создавай параллельные ветки и треды без согласия пользователя. Каждый этап: ветка от свежего main → PR → вливание → следующий этап. Порядок этапов — `docs/06_zadanie.md`, раздел 8.
10. **Логические изменения расчёта** — отдельные PR с заголовком «Расчёт:»: что было, что стало, на сколько изменился итог, источник.
11. **Регрессия по Дербеневской** (`tests/cases/derbenevskaya_legacy.yaml`): расчёт «как в исходном Excel» воспроизводит `reconciliation_targets`. Список ожидаемых расхождений с исходным Excel (со ссылкой на пункт `docs/02_legacy_audit.md` и суммой) согласуется с пользователем до того, как фиксируется в тесте.

## Происхождение значений (задание, раздел 5)

У каждого значения — источник со ссылкой и одна метка:
- **«из источника»** — найдено в документе или системе, ссылка и дата;
- **«оценка по аналогам»** — система посчитала по рынку, показан диапазон и список аналогов;
- **«Экспертное значение»** — задано человеком: кто, когда, на чём основано; в интерфейсе требует автора, обоснование и диапазон min–max, такие значения попадают в чувствительность;
- **«по справочнику»** — стандартное значение из справочника (клик открывает строку справочника).

Финансист подтверждает или меняет любое значение. Изменение фиксируется в истории. Пустое значение не равно нулю: показатель отмечается как «не учтено».

## Правила текста и оформления (задание, раздел 7)

- Читатель — финансист. Каждый блок, фраза и цифра несут информацию для решения; если элемент ничего не сообщает — его нет.
- Никаких технических кодов и текстов для разработчика: идентификаторы формул, ключи YAML, «этап N», «ядро», англицизмы при наличии русского термина.
- «Как посчитано» — 1–3 предложения: что считаем → из чего → пример на числах проекта.
- Вместо «решение компании» — «Экспертное значение». Отличия от Excel — «расхождения», не «ошибки». Итоговый экран — «Дашборд».
- Цвета: жёлтый — не хватает значения; красный — расхождения, «перепроверить»; зелёный — сходится, подтверждено; серый — нет данных.
- Числа по-русски: пробел в тысячах, запятая в дробях, один масштаб в таблице. Проценты вводятся и показываются в % (5 % годовых), надбавки — в п.п.
- Сообщения проверок: что не так → числа → что сделать.
- Не выдумывать источники, ставки и нормативы. Нет источника — вопрос пользователю.

## Проверка текстов

После PR, в которых менялись экраны, тексты или выгрузка, запусти быструю проверку скиллом finmodel-cleanup-loop (только изменённое, один проход). Полная проверка — только перед показом руководителю, перед релизом или по просьбе пользователя.

## Работа агента с репозиторием

- **Данные читать точечно.** `data/*.yaml` и `legacy/*.csv` не читать целиком: найти нужный ID через `grep -n` и читать ±40 строк вокруг (`sed -n`/`Read` с `offset` и `limit`).
- Сгенерированное не читать: `packages/spec/src/generated/**`, `packages/excel-import/src/generated/**`, `docs/03–05`. Чтение запрещено в `.claude/settings.json`; смотреть надо исходные `data/*.yaml` и `legacy/*.csv`.
- **Не запускать много субагентов параллельно.** Каждый заново загружает CLAUDE.md и заново ищет по тем же большим YAML и CSV. Работу этапа вести в одной сессии; субагент — только для действительно независимой задачи, и тогда передать ему в задании уже найденные ID, файлы и строки.

## Команды

```bash
python scripts/validate_spec.py      # проверка реестров, ссылок, графа формул, карты legacy — должна быть 0 ошибок
python scripts/render_docs.py        # сборка docs/03–05 из YAML локально (в git не коммитятся, в CI собираются сами)
python scripts/build_legacy_map.py   # пересборка карты исходного Excel (код выхода 0 = всё сопоставлено)
python scripts/build_legacy_case.py  # пересборка tests/cases/derbenevskaya_legacy.yaml
pnpm spec:build                      # data/*.yaml → packages/spec/src/generated (после любого изменения data/)
pnpm map:build                       # legacy/legacy_values_map.csv → packages/excel-import/src/generated
pnpm test                            # vitest: примеры формул + регрессия по Дербеневской + сверка с исходным Excel
pnpm typecheck && pnpm lint
pnpm build                           # сборка интерфейса
```

## Определение «готово» для любого PR

- [ ] `validate_spec.py` — 0 ошибок; новых предупреждений `needs_verification` нет или они объяснены в описании PR.
- [ ] Для каждой изменённой формулы: обновлены `expr`, `rationale`, `example`; тест на `example` проходит.
- [ ] CI зелёный: `render_docs.py` отработал без ошибок (docs/03–05 в PR не входят).
- [ ] Сверка с `tests/cases/derbenevskaya_legacy.yaml → reconciliation_targets` проходит в расчёте «как в исходном Excel».
- [ ] У каждого показанного значения есть метка происхождения и цепочка до источников со ссылками.
